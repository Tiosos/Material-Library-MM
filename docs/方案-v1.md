# Material Library 通用材料库 · 方案 v1

> 定位：一份**独立于任何业务系统的材料主数据（MDM）**。既能单独当查询站用，也能被 joineryflow 或其它系统通过 API / 文件 / SDK 引用导入。
> 参考来源：`github.com/Tiosos/joineryflow`（FastAPI + Postgres + Next.js，Catalog 模块 9 张材料表、14 种产品类型）。
> 版本：v1（待反馈迭代）

---

## 0. TL;DR

| 项 | 结论 |
|---|---|
| 数据模型 | **一张 core 表 + 类型画像 + 属性 KV**，替掉 joineryflow 的 9 张物理表（但保留 100% 字段与双向映射） |
| 主键 | `material_uid`（ULID，`mat_xxx`），跨系统永久稳定；不再用 `(material_type, id)` 组合引用 |
| 搜索 | **四级降级检索**：精确/前缀 → 加权全文（AND）→ 自动放宽（OR）→ trigram 容错 + 拼写建议 |
| 交付形态 | ① Postgres 服务 + REST API ② 单文件 SQLite 库（零依赖、可拷走）③ JSONL/CSV 导出 ④ 查询站 |
| 集成 | OpenAPI + JSON Schema + Python/TS SDK + MCP server（让 AI 直接查） |
| 首个里程碑 | **Phase 1（2 周）**：导入 joineryflow 9 表 + 一个能用的搜索框 |

已随方案附带一个**可运行原型**（`proto/`），可以直接搜，用来验证"缺省搜索"的手感。

## 1. 需求理解：什么叫"关键词可以缺省搜索"

这是本方案的核心诉求。我把它拆成 **四层缺省**，方案要四层全支持：

| 层 | 场景 | 例子 | 手段 |
|---|---|---|---|
| **L1 输入缺省** | 懒得打完 | `blu` → Blum 五金 | 前缀匹配 + 补全 |
| **L2 命中缺省** | 多个词只记得几个，不必全中 | `blum soft close hinge` 里只输 `blum hinge` | 先 AND，无结果自动降为 OR，按命中数排序 |
| **L3 维度缺省** | 不知道该搜哪个字段 | 输 `18mm black` 就能找到 18mm 黑板 | 一个框搜全部字段（SKU/名称/品牌/供应商/规格/颜色/同义词） |
| **L4 拼写缺省** | 拼错、用俗称、中英混 | `luminux`/`melamine`/`MDF`/`中纤板` | trigram 相似度 + 同义词表 + 分词 |

再加一条体验约束：**零结果时不要白屏**，要给出"你是不是要找 X"和放宽条件后的近似结果。

## 2. 现状盘点：joineryflow 已经有什么

从仓库实读（不是猜）：

**资产（可直接复用）**
- 9 张材料表：`board / edging / glass / timber / benchtop / hardware / appliance / custom_made / equipment_hire`，由 `catalog/queries.py::REGISTRY` 统一驱动，字段定义集中在 `*_FIELDS_TUPLE`
- 14 种产品类型页签（其中 6 种复用表、无独立表）
- 公共列：`sku / description / synonyms / default_supplier(_id) / default_lead_time_days / unit_cost / product_type / archived_at,archived_by / workspace_id`
- 各类型专属字段：板的 `colour/substrate/finish/sided/grain/rating/hmr/尺寸`、玻璃的 `glass_type/edge_finish/power_point`、封边的 `edge_type/roll_length_m/glued` 等
- 单价回落规则：`unit_cost` 为空时用各表自己的成本列（`cost_per_sheet`/`cost`/`cost_per_slab`/`cost_per_unit`）
- 采购历史接口：`GET /catalog/{slug}/{mid}/purchase-history` —— 天然的**价格历史数据源**
- 软归档、workspace 隔离、图片 blob、CV 供应商码映射（`cv_material_mapping`）

**痛点（方案要解决）**

| # | 问题 | 影响 |
|---|---|---|
| P1 | 搜索是 `description ILIKE '%q%' OR sku ILIKE '%q%' OR product_type ILIKE '%q%'`，单关键词 | 多词、错拼、俗称全部搜不到 |
| P2 | 无排序，无相关性 | 结果靠插入顺序，常用料排不到前面 |
| P3 | 跨类型要切页签，API 层是 `for type_ in REGISTRY` 扫 9 次 | 想找"18mm 黑"不知道在哪个 tab |
| P4 | 主键是表内自增，跨表引用靠 `(material_type, id)` 组合 | 没法给外部系统一个稳定 ID，导入即失效 |
| P5 | 无来源溯源、无版本、无价格历史、无标准导出格式 | 不敢当"主数据"往外发；对不上账 |

## 3. 架构总览

```
                    ┌──────────────────────────────┐
   joineryflow ────▶│   ingest / ETL (映射规范)     │
   FileMaker  ────▶│  全量 + 增量 (since=)         │
   CSV / 手工 ────▶│  冲突留痕, 不静默覆盖         │
                    └──────────────┬───────────────┘
                                   ▼
                    ┌──────────────────────────────┐
                    │  Material Library (core)     │
                    │  material + identifier       │
                    │  + price + relation          │
                    │  + profile（类型画像）        │
                    └──────────────┬───────────────┘
                                   ▼
     ┌─────────────────┬───────────┴────────┬──────────────────┐
     ▼                 ▼                    ▼                  ▼
 查询站 (Web)      REST / GraphQL       导出 (JSONL/      MCP server
 缺省搜索+筛选     API + SDK            CSV/Parquet)     (AI 直接查)
     │                 │                    │                  │
     └─────────────────┴────────────────────┴──────────────────┘
                                   ▼
              反向 write-back → joineryflow PATCH /catalog/{slug}/{mid}
```

**关键决策：Material Library 是独立服务，不塞进 joineryflow。**
理由：joineryflow 的材料是"带 workspace 的业务数据"，而主数据要跨 workspace、跨系统复用。两者用 `material_uid` 关联，而不是合并。

## 4. 数据模型：Universal Material Record (UMR)

完整 DDL 见 [`schema/material.sql`](../schema/material.sql)，交换格式见 [`schema/material.schema.json`](../schema/material.schema.json)。

### 4.1 五张表

| 表 | 作用 | 解决的问题 |
|---|---|---|
| `material` | 核心记录（分类、名称、品牌、单位、单价、属性、同义词…） | P3：一张表统一 9 类 |
| `material_identifier` | 编码簿：`sku / ean / supplier_code / legacy_id / cv_code / slab_id / model_no` | P4：任何系统的编码都能反查 |
| `material_price` | 价格历史（供应商、有效期、阶梯价） | P5：单价不再是个裸数字 |
| `material_relation` | 替代料 / 配件 / 升级替代 | 缺料时立刻给替代项 |
| `material_profile` | 类型画像（JSON Schema 定义该类型有哪些专属字段） | 新增第 10 种材料不用改表 |

### 4.2 关键设计：core + attributes，而不是 9 张表

```jsonc
{
  "material_uid": "mat_01J8ZQ8K3M5N7P9R2T4V6X8Y0A",
  "category": "board",
  "product_type": "Board",
  "name": "16mm Black Melamine",
  "brand": "Laminex Australia",
  "unit": "sheet",
  "unit_cost": 40.00,
  "currency": "AUD",
  "cost_basis": "ex_gst",
  "lead_time_days": 5,
  "default_supplier": "Laminex Australia",
  "synonyms": ["16-BLACK", "black melamine board", "melamine", "MDF black"],
  "tags": ["common", "carcass"],
  "attributes": {
    "thickness_mm": 16, "colour": "Black", "substrate": "MDF",
    "sheet_len_mm": 3600, "sheet_wid_mm": 1200, "finish": "Melamine", "sided": "Double"
  },
  "identifiers": [
    { "kind": "sku",       "value": "16-BLACK", "source_system": "joineryflow", "is_primary": true },
    { "kind": "legacy_id", "value": "BM-201",   "source_system": "joineryflow" }
  ],
  "source_system": "joineryflow",
  "source_id": "42",
  "source_payload": { "...": "原始行快照，用于对账和回滚" }
}
```

**为什么不直接沿用 9 张表？** 因为"通用材料库"会不断加类型（耗材、油漆、五金配件…），每加一种就建一张表是不可持续的。core 表 + profile 校验 = 既灵活又不失控。映射层保证 joineryflow 的每行每字段都能 1:1 来回。

### 4.3 与 joineryflow 的映射

完整规范见 [`mapping/joineryflow.yaml`](../mapping/joineryflow.yaml)。要点：

- 9 张表 → `category` 九个值；专属字段原样进 `attributes`（**键名不改**，便于回写）
- `sku/code/internal_ref/slab_id/model_number/contract_ref` 全部登记进 `identifier`
- `unit_cost` 沿用上游回落规则（`COALESCE(unit_cost, 自有成本列)`）
- `archived_at` → `status=archived`，永不硬删
- 回填走 `PATCH /catalog/{slug}/{mid}`；**禁止**回写归档状态、**禁止**改动报价上已快照的价格

## 5. 搜索设计（方案重点）

### 5.1 检索管道：四级降级（Graceful Degradation）

用户敲一个词，按序尝试，一旦有结果就停；结果里标注"这是放宽后的结果"：

```
q ──▶ L0 精确/前缀命中（identifier 精确 = 编码；名称前缀匹配）
      │  无结果 ↓
      ├──▶ L1 加权全文 AND（所有词都必须出现）         ← 默认路径
      │      无结果 / <3 条 ↓
      ├──▶ L2 放宽为 OR（按命中词数 + 字段权重排序）    ← "缺省搜索"核心
      │      无结果 ↓
      └──▶ L3 trigram 模糊 + 同义词扩展 + 拼写建议      ← 错字/俗称
```

这样"打多了词"不会搜不到，"打错了字"也不会白屏。

### 5.2 字段权重（解决 L3 维度缺省）

生成列 `search_tsv`，四级权重：

| 权重 | 字段 | 理由 |
|---|---|---|
| **A** | 全部 identifiers（sku/code/ean/供应商码/legacy id） | 输编码是最精确意图 |
| **B** | `name` `brand` `model_no` | 名称/品牌 |
| **C** | `default_supplier` `product_type` `category` `unit` | 分类维度 |
| **D** | `description` `attributes` `synonyms` `tags` | 兜底，量大 |

```sql
-- L1：加权全文 AND，带相关性排序
SELECT material_uid, name, category, unit_cost,
       ts_rank_cd('{0.1,0.2,0.4,1.0}'::float4[], search_tsv, query) AS score
FROM material, websearch_to_tsquery('simple', :q) query
WHERE search_tsv @@ query AND status <> 'archived'
ORDER BY score DESC, ref_count DESC
LIMIT 50;
```

### 5.3 自动放宽（解决 L2）

```sql
-- L2：先算每词是否命中，再按"命中词数 DESC, 权重分 DESC"排
WITH q AS (SELECT unnest(string_to_array(:q, ' ')) AS term)
SELECT m.*,
       COUNT(DISTINCT q.term) FILTER (WHERE m.search_tsv @@ plainto_tsquery('simple', q.term)) AS hits
FROM material m CROSS JOIN q
WHERE m.status <> 'archived'
  AND EXISTS (SELECT 1 FROM q WHERE m.search_tsv @@ plainto_tsquery('simple', q.term))
GROUP BY m.material_uid
ORDER BY hits DESC, ts_rank_cd(m.search_tsv, plainto_tsquery('simple', :q)) DESC
LIMIT 50;
```

### 5.4 模糊与拼写建议（解决 L4）

```sql
-- L3：trigram 相似度；同时给出"你是不是要找"
SELECT material_uid, name, similarity(name, :q) AS sim
FROM material
WHERE name % :q OR description % :q
   OR EXISTS (SELECT 1 FROM unnest(synonyms) s WHERE s % :q)
ORDER BY sim DESC LIMIT 20;
```

- `pg_trgm` GIN 索引支撑 `%` 相似度与前缀加速
- **同义词表**从三处自动积累：上游 `synonyms` 列、历史搜索被点选的纠错、人工维护的别名表
- 中英文混排：`simple` 词典不分词中文，中文走 `pg_trgm` bigram；如需中文分词再上 `pg_jieba`/`zhparser`（建议 Phase 3 再评估）

### 5.5 排序（解决 P2 无相关性）

```
final_score = 0.55 * text_relevance
            + 0.20 * popularity(ref_count, search_hits 归一化)
            + 0.15 * exactness(编码精确命中 = 1，否则 0)
            + 0.10 * freshness(近期用过/近期更新)
            − penalty(archived 大幅降权但不隐藏)
```

### 5.6 查询语法（给高级用户，但不强制）

| 写法 | 含义 |
|---|---|
| `blum hinge` | 默认：AND，放宽后 OR |
| `blum -hinge` | 排除 |
| `"soft close"` | 精确短语 |
| `thickness:18 colour:black` | 按属性过滤（属性名来自 profile） |
| `supplier:laminex 18mm` | 混合 |
| 空查询 | 返回"最近常用 / 最近更新"，而不是空白 |

### 5.7 Facet 筛选

右侧常驻：分类（9 类）、品牌、供应商、单位、价格区间、归档开关；按类型动态出现的属性筛选（如 board 的 thickness / colour，glass 的 glass_type）。**筛选与搜索是叠加关系，不是二选一。**

## 6. 如何被其它系统引用 / 导入

| 方式 | 适用 | 说明 |
|---|---|---|
| **REST API** | 在线系统 | `GET /v1/materials?q=&category=&limit=&cursor=`、`GET /v1/materials/{uid}`、`POST /v1/materials/bulk` |
| **增量同步** | 保持两个系统一致 | `GET /v1/materials?since=<updated_at>`；外部系统只存 `material_uid` |
| **文件导入** | 一次性 / 离线 | `materials.jsonl`（一行一条，流式）、`materials.csv`（属性展开为 `attr_*` 列）、Parquet |
| **契约** | 生成客户端 | OpenAPI 3.1 + JSON Schema，可自动生成 Python/TS/C# 客户端 |
| **SDK** | 开发体验 | `pip install materiallib` / `npm i @materiallib/client`，一行 `search("blum hinge")` |
| **MCP server** | AI/LLM 调用 | 把材料库暴露成工具，Copilot/Claude 可直接问"18mm 黑板多少钱" |
| **单文件 SQLite** | 嵌入 / 便携 | 整个库打包成一个 `.sqlite`，拷给谁都能查，零依赖 |

**引用侧约定（写进契约，很重要）**
1. 外部系统**只存 `material_uid`**，不要存本地自增 ID
2. 需要快照价格时**连同 `valid_from` 与 `source_system` 一起存**，不要只拷数字
3. 材料被归档时外部系统**不应崩溃**，按"历史有效"处理

## 7. 查询站 UI（独立可用）

- **顶部一个大搜索框**，聚焦快捷键 `/`，输入即搜（debounce 150ms）
- **左侧分类树**（9 类 + 常用/收藏），**右侧结果卡片**（图 + 名称 + SKU + 供应商 + 单价 + 关键属性标签）
- **结果区顶部**：命中数、用了哪一级检索（"精确 / 放宽 / 模糊"）+ 一键"只看精确"
- **零结果页**：拼写建议 + 放宽后结果 + "用 XX 搜到 N 条"
- **详情页**：全部属性、价格历史曲线、替代料、采购历史、原始来源、复制 UID / 导出 JSON
- **批量动作**：勾选 → 导出 JSONL/CSV；生成分享链接
- 技术：复用 joineryflow 现有 Next.js 风格（Inter + JetBrains Mono、设计 token），或做成极简静态站

## 9. 选型建议与备选

| 维度 | **建议** | 备选 | 取舍理由 |
|---|---|---|---|
| 存储/检索 | **PostgreSQL**（`tsvector` + `pg_trgm`） | Meilisearch / Typesense / ES | PG 与 joineryflow 同栈，运维零新增；数据量 <50 万行时 PG 足够。**若要求"开箱即用的错字容错 + 中文分词 + 毫秒级"，换 Meilisearch 更省事**（它原生支持 typotolerance，本方案 L3 可整个交给它） |
| 单机/嵌入 | **SQLite + FTS5** | DuckDB | 原型与"拷走就能用"场景 |
| API | **FastAPI** | — | 与 joineryflow 一致，OpenAPI 白送 |
| 前端 | 复用 joineryflow Next.js | 静态 HTML | 视是否要并进现有系统 |
| 主键 | **ULID** | UUID v7 | ULID 字典序 ≈ 时间序，索引友好、可读 |
| 语义检索 | `pgvector`（后期） | 外部向量库 | 只有确实需要"意图搜索"才上 |

> **一条重要建议**：先别上搜索引擎。用 PG 全文本 + trigram 把 P1–P2 做完，用真实数据测"搜不到"的抱怨率；如果仍然高，再引入 Meilisearch——此时数据管道已就绪，切换成本很低。

## 10. 需要你拍板的问题（决定 v2 怎么写）

1. **数据范围是只搬 joineryflow 的 9 类，还是也要纳入耗材/油漆/包装等？**（影响 profile 设计）
2. **主数据权属**：Material Library 是唯一真源（joineryflow 变成消费方），还是双向同步？我倾向前者，但 write-back 会受限。
3. **workspace 如何处理**：主数据跨 workspace 共享（板材是全球唯一的），还是每个 workspace 一份？我倾向**全局共享 + workspace 可覆盖价格/供应商**。
4. **部署形态**：独立服务 / 单文件 SQLite / 两者都要？
5. **中文支持**：现在材料名是英文为主，需要中文名与中文搜索吗？
6. **价格是否进库**：搬 `unit_cost` 之外，要不要搬采购历史做价格曲线？（我倾向要，但要确认没有商务敏感问题）
